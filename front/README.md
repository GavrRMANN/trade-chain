# Trade Chain — Frontend

Адаптивное React-приложение для прямого и многошагового обмена товарами. Главная задача frontend — превратить сложный поиск пути между желаниями пользователей в понятный сценарий:

```text
Мой товар → Ближайший обмен → Желаемая цель
```

Интерфейс помогает выбрать стартовый товар и цель, показывает текущее положение в маршруте, предлагает следующий обмен и сохраняет контекст цели между этапами.

## Продуктовая основа

Перед разработкой сценария были сформулированы три гипотезы:

1. Пользователю понятнее сначала выбрать свой товар, а затем желаемую цель.
2. Пользователи готовы рассматривать цепочку из двух-трёх обменов, если могут сравнить варианты.
3. Прозрачность участников, выгоды и условий повышает доверие к многошаговому обмену.

Для качественной проверки MVP команда провела пять глубинных интервью среди друзей и знакомых участников команды. Исследование не претендует на статистическую репрезентативность, но помогло обнаружить повторяющиеся ожидания:

- 4 из 5 респондентов лучше поняли последовательность «что отдаю → что хочу»;
- 3 из 5 готовы рассматривать короткий маршрут при наличии выбора;
- всем респондентам важно видеть условия, статус и понятное следующее действие.

На основе интервью были сформированы User Stories, Epics и пользовательский сценарий. Поэтому интерфейс не показывает весь граф обменов, а держит в фокусе текущий товар, цель и ближайший шаг.

## Возможности frontend

- авторизация, демонстрационные аккаунты и защищённые маршруты;
- каталог товаров в формате сетки и вертикальной ленты;
- поиск, категории и карточка товара;
- создание, редактирование и архивирование объявлений;
- личные и публичные профили, списки желаний и отзывы;
- прямое предложение обмена;
- построение пути к конкретному товару или категории;
- выбор нескольких вариантов следующего обмена;
- список обменов, комната сделки, чат и подтверждение результата;
- уведомления и обновление интерфейса в реальном времени.

## Основной сценарий

1. Пользователь выбирает своё активное объявление.
2. Выбирает конкретный товар или категорию, к которой хочет прийти.
3. Frontend открывает персональный маршрут и получает доступные шаги.
4. Пользователь видит текущий товар, цель, оставшееся количество обменов и ближайшие варианты.
5. Отправляет одно или несколько независимых предложений.
6. После завершённого обмена полученный товар становится новой точкой маршрута, а предыдущий шаг сохраняется в истории.

На desktop выбор стартового товара и цели отображается одновременно. На мобильном та же форма превращается в последовательный двухшаговый процесс с действиями «Продолжить» и «Назад».

## Архитектура

Frontend организован по Feature-Sliced Design:

```text
src/
├── app/       # провайдеры, Redux store, маршрутизация, realtime
├── pages/     # сборка экранов и страничных сценариев
├── widgets/   # крупные самостоятельные блоки страниц
├── features/  # пользовательские действия и бизнес-сценарии
├── entities/  # типы, RTK Query API и UI доменных сущностей
└── shared/    # общий API-клиент, хуки, утилиты и UI-компоненты
```

Компоненты преимущественно отвечают за отображение и пользовательские события. Работа с запросами, состояниями и вычислениями вынесена в кастомные хуки:

- `RouteBuilder` / `useRouteBuilder` — выбор стартового товара и цели;
- `TargetProductPicker` / `useTargetProductPicker` — поиск товара или категории;
- `RoutePage` / `useRoute` — сборка маршрута, истории и предложений;
- `RouteRecommendations` / `useRouteRecommendations` — выбор вариантов и мобильные жесты;
- `ExchangeRoomPage` / `useExchangeRoom` — состояние комнаты обмена.

Такое разделение оставляет JSX читаемым, упрощает переиспользование компонентов и изолирует сложную логику от представления.

## Интересные реализации

### Путь к цели как устойчивый пользовательский сценарий

Стартовый товар и цель становятся частью адреса страницы. Благодаря этому маршрут можно перезагрузить, открыть по прямой ссылке или продолжить после перехода на другой экран без потери контекста.

Frontend различает:

- подтверждённый шаг найденного маршрута;
- дополнительные варианты прямого обмена;
- уже отправленные и активные предложения;
- завершённые шаги, формирующие историю пути.

При отправке предложения сохраняются цель, текущий этап и связь с предыдущим обменом. Новое предложение остаётся частью общего пути, а не превращается в независимую сделку.

### Несколько предложений с частичным успехом

Пользователь может выбрать несколько вариантов следующего обмена. Запросы отправляются независимо через `Promise.allSettled`: успешные предложения сохраняются, а неуспешные остаются выбранными для повторной отправки. Ошибка одного запроса не отменяет остальные результаты.

### RTK Query и единый жизненный цикл данных

Каждая доменная сущность имеет типизированный API-срез на RTK Query. Общий `apiBaseQuery` добавляет JWT к авторизованным запросам, а теги управляют точечным обновлением кэша.

Отдельный middleware синхронизирует кэш с пользовательской сессией:

- очищает данные предыдущего аккаунта при входе, выходе или смене пользователя;
- завершает сессию при ответе `401`;
- обновляет связанные сущности после изменения состояния обмена.

### Realtime без постоянного polling

Приложение поддерживает авторизованную SSE-подписку. События чата, изменения обменов и завершение сделки инвалидируют только затронутые RTK Query-теги. Например, новое сообщение обновляет кэш чата и уведомлений, но не перезагружает весь список обменов.

При разрыве соединения frontend автоматически переподключается, а после восстановления сети RTK Query актуализирует необходимые данные.

### URL-управляемые модальные окна

Авторизация, предложение обмена, архивирование товара и построение маршрута открываются как маршруты. `backgroundLocation` сохраняет страницу под модальным окном, но тот же адрес работает и как прямая ссылка после перезагрузки.

Публичные и защищённые модальные маршруты описаны централизованно. Тяжёлые страницы и модальные окна загружаются через `React.lazy` и `Suspense` только при открытии.

### Адаптивная выдача рекомендаций

На desktop варианты следующего обмена представлены рядом карточек. На мобильном используется последовательный просмотр со свайпами, индикатором позиции и обычными кнопками как доступной альтернативой жестам.

Поиск цели использует `useDeferredValue`, чтобы фильтрация списка не блокировала ввод. В выдачу не попадают собственные и неактивные товары, а стартом маршрута может быть только активное объявление текущего пользователя.

### Чистые преобразования данных

Сложные преобразования вынесены из компонентов в чистые функции. Например, `orderChainForRoute` определяет направление полученной цепочки по старту и цели, возвращает путь в порядке прохождения пользователем и не изменяет исходный массив.

В отдельных функциях также собраны:

- контекст предложения обмена;
- группировка обменов по общей цели;
- вычисление требуемого от пользователя действия;
- форматирование статусов и данных интерфейса.

### Состояния и доступность

Для основных сценариев предусмотрены загрузка, пустые результаты, ошибки API, частичный успех и повторные действия. Интерактивные элементы поддерживают keyboard focus, выбранные карточки передают состояние через `aria-pressed`, а сообщения об успехе и ошибках объявляются через `role="status"` и `role="alert"`.

## Запуск

### С локальным mock API

В первом терминале:

```bash
cd front
npm install
npm run mock-api
```

Во втором терминале:

```bash
cd front
npm run dev
```

По умолчанию frontend доступен на `http://localhost:5173`, а API ожидается на `http://localhost:3001`.

### С backend в Docker

Из каталога `front/`:

```bash
npm run dev:docker
```

Скрипт поднимает API и PostgreSQL через Docker Compose, дожидается готовности API и запускает Vite.

### Весь проект в Docker

Из корня репозитория:

```bash
docker compose up --build
```

Адрес API можно переопределить переменной `VITE_API_BASE_URL`.

## Проверка качества

- Unit-тесты покрывают чистые функции, форматирование, маршрутизацию модальных окон и ключевые правила обмена.
- Storybook содержит обычные, загрузочные, пустые, ошибочные и интерактивные состояния компонентов.
- Playwright проверяет сквозные сценарии товаров, профилей и обменов.
- Production-сборка выполняет проверку TypeScript перед сборкой Vite.

Перед отправкой изменений рекомендуется выполнить:

```bash
npm run lint
npm test
npm run build
```

## Ограничения MVP

- Поиск целевого товара выполняется по ограниченной клиентской выборке; при росте каталога его следует перенести на серверную пагинацию.
- Frontend-проверки принадлежности маршрута нужны для корректного UX, но не заменяют серверную авторизацию.
- Исследование основано на небольшой учебной выборке; перед продуктовым запуском гипотезы необходимо проверить на более широкой аудитории.

## Использование инструментов на основе ИИ

При разработке frontend применялись инструменты на основе ИИ для поиска логических ошибок, локального рефакторинга, редактирования текста (этого например (* ^ ω ^) ) и подготовки демонстрационного MVP по результатам интервью. Все изменения проверялись командой, а ответственность за продуктовые и технические решения оставалась за разработчиками.
