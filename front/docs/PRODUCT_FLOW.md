# Логика продукта и экранов (Product Flow)

Документ описывает предметную область, роли, каждый экран приложения и связи
между ними с точки зрения **пользователя** и **владельца товара**. Это источник
правды для фронтенд-MVP. Backend менять нельзя — поэтому здесь зафиксированы и
его ограничения.

> Статус на дату: 2026-08-09. Документ отражает текущее состояние кода.

## 1. Предметная область

Приложение — бартерная площадка (обмен вещами, по образцу Авито). Ядро — обмены.

| Понятие в продукте | Как называется в коде | Где живёт |
|---|---|---|
| Пользователь | `customer` / `user` | `entities/customer`, `entities/user` |
| Товар (объявление) | `product` | `entities/product` |
| Желаемое взамен (категории) | `wishlist` + `wishlist_option` | `entities/wishlist` |
| Предложение обмена / сделка | **`chain`** | `entities/chain` |
| Сообщение по сделке (чат) | `chain_message` | `entities/chain` (`TChainMessage`) |
| Отзыв после обмена | `review` | `entities/review` |
| Категория | `category` | `entities/category` |
| Маршрут до цели (несколько звеньев) | результат `GET /search/chain` | `entities/search` |

**Важно про терминологию:** в продукте «обмен» — это сделка между двумя людьми.
В коде это **`chain`** (одно звено). «Цепочка/маршрут» из нескольких обменов до
цели — это не таблица, а результат поиска `GET /search/chain` (BFS по графу
товаров). Система **не фиксирует** сложную цепочку участников — она лишь ведёт
пользователя от звена к звену (см. кейс, строки 4–5, 29).

### 1.1 Два сценария обмена (из кейса)

1. **Прямой обмен.** Юзер видит объявление, чей вишлист пересекается с его
   товарами → предлагает свой товар → владелец принимает/отклоняет/встречное →
   чат → подтверждение результата обеими сторонами → отзыв.
2. **Обмен до цели (маршрут).** Юзер открывает желанный товар, система строит
   путь `текущий → … → цель`. Активно только первое звено. После успешного
   обмена юзер переходит к следующему звену.

### 1.2 Жизненный цикл сделки (`chain.status`)

Статус-машина (бэкенд, `internal/exchange/exchange.go`):

```
pending ──(получатель accept)──> active ──(обе стороны confirm success)──> completed
  │                                  └──(одна сторона success=false)────> failed
  ├──(получатель reject)──> rejected        [терминальный]
  ├──(получатель counter)──> countered      [терминальный]
  ├──(инициатор cancel)───> cancelled       [терминальный]
  └──(система, TTL 72ч)───> expired          [терминальный]
```

- `pending` — предложение отправлено, ждёт ответа владельца.
- `active` — владелец принял, стороны договариваются в чате.
- `completed` — обмен состоялся (бэкенд swaps владельцев товаров).
- `failed` — договорились, но обмена не было.
- `rejected` / `cancelled` / `expired` / `countered` — терминальные.

**Кто что может** (бэкенд):
- Получатель (`recipient_id`) → `active` / `rejected` / `countered` (`PATCH /status`).
- Инициатор (`initiator_id`) → `cancelled` (`PATCH /status`).
- Обе стороны при `active` → `POST /confirm {success}`.
- «Встречное предложение» (`countered`) **не несёт payload** — только смена
  статуса + текст в чате. Полноценного counter-offer с другим товаром в API нет.

### 1.3 Статусы товара (`product.status`)

`active` | `reserved` | `exchanged` | `archived`.

- `active` — участвует в обменах, виден в каталоге.
- `exchanged` — обменян (бэкенд ставит при `completed`).
- Создать можно `active`/`reserved`/`exchanged`; `archived` — только через
  `PATCH` (UI для снятия с обмена нет).

## 2. Роли и что они видят

Приложение различает четыре «режима просмотра» одного и того же экрана:

| Режим | Условие | Что важно |
|---|---|---|
| **Гость** | нет токена | Не видит обмены/профиль/маршрут. Кнопки действия открывают `/auth`. |
| **Зритель (чужой товар)** | авторизован, не владелец | Видит «Предложить обмен», вишлист владельца, свои подходящие вещи, маршрут. |
| **Владелец товара** | `product.customer_id === currentUser` | Видит «Редактировать», счётчик входящих предложений, редактор вишлиста. |
| **Инициатор сделки** | `chain.initiator_id === currentUser` | В сделке видит «Отменить предложение». |
| **Получатель сделки** | `chain.recipient_id === currentUser` | В сделке видит «Принять/Встречное/Отклонить». |

> Имя/аватар/рейтинг пользователя — **не** хранятся на `customer`. Email есть,
> рейтинг считается на лету через `GET /reviews/by-customer/:id/rating`.

### 3.1 Шапка (`widgets/headerMenu`)

- Логотип → `/` (каталог).
- Поиск (`SearchBox`): ввод → саджесты из категорий/товаров → Enter ведёт на
  `/?q=`. На мобиле — отдельный `MobileHeaderMenu`.
- **«Разместить»** → если авторизован `/create`, иначе модалка `/auth`.
- **«Обмены»** → если авторизован `/exchanges`, иначе `/auth`.
- **«Профиль»** → если авторизован `/profile`, иначе `/auth`.
- `MobileNavBar` сейчас **заглушка** (`return null`) — нижней навигации нет.

### 3.2 Каталог / Главная (`/`, `pages/catalog`)

- Быстрые фильтры-категории (`WhiteBox`), включая «Все».
- Сетка `ProductCard`. Заголовок зависит от `?q` / `?category_id`.
- Пустая категория → «Добавить товар» → `/create`.
- Клик по карточке → `/product/:id`.
- **Сейчас НЕ реализовано из кейса (US-8):** «товары, на которые могу обменять
  свои, — выше». Каталог просто грузит `GET /products`, без приоритизации по
  совпадению с вишлистом пользователя.

### 3.3 Карточка товара (`/product/:id`, `pages/product`)

**Общее (все роли):** герой (фото, характеристики, описание), блок продавца с
рейтингом, до 3 отзывов, блок «что хочет взамен».

**Зритель (чужой товар):**
- «Предложить обмен» → `OfferExchangeModal`.
- Вишлист владельца (категории, что он хочет взамен).
- «Ваши подходящие вещи» — `matchingProducts` (мои товары, чья категория есть в
  вишлисте владельца). Если есть совпадение — кнопка «Построить маршрут обмена».
- Если прямого совпадения нет, но `routeChain.length>1` — превью маршрута
  `ChainRow` + «Открыть маршрут».
- Если ничего нет — «Предложить другой товар» (тот же модал).

**Владелец товара:**
- «Редактировать» → `/product/:id/edit`.
- «Входящих предложений: N» + «Перейти к предложениям» → `/exchanges`.
- `WishlistEditor` — управляет категориями «хочу взамен».

**Навигация наружу:** в шапке «Обмены»/«Профиль»; внутри — на другие карточки
(через matches/chain) и на маршрут.

### 3.4 Создание/редактирование товара (`/create`, `/product/:id/edit`)

- Форма: название, описание, цена, категория, локация, фото, статус.
- Гостя и чужого владельца пускает в `/auth`.
- `?target` редактирования — повторно использует `CreateProductPage`.

### 3.5 Маршрут обмена (`/route?target=:id`, `pages/route`)

- Грузит `GET /search/chain?target_product_id=` → массив товаров-звеньев.
- `ChainRow` рисует `текущий → ... → цель`.
- «Предложить обмен» (первое звено) и «Предложить другой товар напрямую» (цель)
  открывают `OfferExchangeModal` → после успеха редирект на `/exchanges/:chainId`.
- Гостя → `/auth`; пустой маршрут → «Предложить другой товар напрямую».

### 3.6 Мои обмены (`/exchanges`, `pages/exchanges`)

- `GET /chains/my` → все сделки (и как инициатор, и как получатель).
- Вкладки: **Входящие** (не терминальные, я получатель) / **Исходящие** (не
  терминальные, я инициатор) / **Завершённые** (любой терминальный статус).
- Строка: `ProductThumb → ProductThumb` + `StatusBadge` + дата. Клик → комнату.
- Гостя → `/auth`.

### 3.7 Комната обмена (`/exchanges/:chainId`, `pages/exchangeRoom`)

- Два товара (`ProductCard horizontal`), статус, дата.
- **Действия** зависят от статуса и роли:
  - `pending`/`countered` + инициатор → «Отменить предложение».
  - `pending`/`countered` + получатель → «Принять» / «Встречное» / «Отклонить».
  - `active` + любая сторона → «Обмен состоялся» / «Не договорились».
  - терминальный → «Сделка завершена, действия недоступны».
- Чат (`MessageList` + `MessageInput`) — `GET/POST /chains/:id/messages`.
- При `completed` — форма отзыва (звёзды + комментарий) → `POST /reviews`.

### 3.8 Профиль (`/profile`, `/profile/:customerId`, `pages/profile`)

- Свои товары (активные / в архиве), рейтинг, кол-во отзывов, выход.
- Публичный профиль (`:customerId`) — чужие товары без выхода.
- **Сейчас НЕ показано:** история обменов, список отзывов (только счётчик).

### 3.9 Авторизация (`/auth` overlay, `pages/auth` + `features/auth`)

- Модалка поверх фона (`backgroundLocation`). Login/Register.
- После успеха токен в `localStorage`, `userSlice` инициализируется, модалка
  закрывается.

## 4. Критический блокер бэкенда (МЕНЯТЬ НЕЛЬЗЯ — только флаг)

В `back/internal/httpapi/router.go:60` строка **закомментирована**:

```go
r.Group(func(r chi.Router) {
    //r.Use(auth.AuthMiddleware)   // ← ЗАКОММЕНТИРОВАНО
    ...
})
```

`AuthMiddleware` единственный кладёт `user_id` в контекст запроса. Все
обработчики `chains`, `search`, `reviews`, `auth/me` начинают с
`auth.UserIDFromContext(ctx)` и при отсутствии значения отвечают **403**.

**Следствие:** сейчас на фронте НЕ работают: создание предложения, список «Мои
обмены», комната обмена, чат, подтверждение, маршрут (`/search/chain`), отзыв,
`/auth/me`. Работают только: `auth/login`, `auth/register`, `products`
(`AuthMiddleware` навешен отдельно в `product.go:31`), `categories`,
`wishlists`, публичные отзывы/рейтинг.

**Действие:** фронтенд делается **полностью готовым** к этим эндпоинтам; для
ручного прогона нужно попросить бэкенд раскомментировать одну строку. Это
отмечено в `TODO` документе.

## 6. Соглашения фронтенда (FSD)

- **Слои:** `app` → `pages` → `widgets` → `features` → `entities` → `shared`.
- **Один компонент — один файл.** Логика — в кастомных хуках `pages/<page>/lib`.
- **UI:** `shared/ui` (кастомные компоненты) + `antd` точечно (`Layout`,
  `Tabs`, `Empty`, `Result`, `ConfigProvider`).
- **Заголовок страницы:** через `usePageTitle()` (контекст), а **не** локальный
  `<h1>`. См. память [[global-pagetitle-context]].
- **CSS:** BEM в CSS-модулях (`block__element`, `block--mod`). См. память
  [[css-bem-convention]].
- **Маршруты-модалки:** `useOpenModalRoute` (сейчас wired только `auth`).
- **Data:** RTK Query, базовый `fetchBaseQuery` с `Bearer` из `getAuthToken()`.
- **«обмен» = `chain`** в коде. См. память [[chain-exchange-integration-gaps]].
