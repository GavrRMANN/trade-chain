# Code Requirements Review Plan

Ты выполняешь ревью frontend-кода проекта на React + TypeScript.

Твоя задача:
1. Найти нарушения требований ниже.
2. Не менять код автоматически.
3. Для каждого нарушения указать:
    - файл;
    - строку или участок кода;
    - нарушенное правило;
    - почему это проблема;
    - насколько критично нарушение;
    - короткий вариант исправления.
4. Не предлагать рефакторинг ради рефакторинга.
5. Если код уже соответствует требованиям — явно это отметить.
6. Учитывать архитектуру проекта и не выносить код в shared только ради устранения дублирования.

---

# 1. Проверка моделирования состояний

## 1.1. Не использовать несколько независимых boolean/state-флагов
для описания одного логического состояния.

Плохо:

const [data, setData] = useState<User | null>(null);
const [loading, setLoading] = useState(false);
const [error, setError] = useState<string | null>(null);

Такой код допускает невозможные комбинации:

loading = true
data !== null
error !== null

Если значения относятся к одному процессу, например API-запросу,
они должны моделироваться единым состоянием.

Предпочтительно:

type State =
| { status: "initial" }
| { status: "loading" }
| { status: "success"; data: User }
| { status: "error"; message: string };

---

## 1.2. Использовать discriminated union для взаимоисключающих состояний

Проверять состояния:

- initial / idle;
- loading;
- success;
- error;
- pending;
- expired;
- queued;
- completed;

и аналогичные.

Если одновременно может существовать только один вариант —
предпочитать union с полем-дискриминатором:

type State =
| { status: "idle" }
| { status: "loading" }
| { status: "success"; data: Data }
| { status: "error"; error: Error };

Не требовать discriminated union для независимых состояний.

Например:

const [isModalOpen, setModalOpen] = useState(false);
const [selectedItem, setSelectedItem] = useState<Item | null>(null);

могут быть независимыми и сами по себе не являются нарушением.

---

## 1.3. Связанные данные и флаги состояния хранить вместе

Если несколько флагов описывают один процесс и связаны с одними и теми же
данными, не хранить их в отдельных независимых `useState`:

Плохо:

const [data, setData] = useState<Data | null>(null);
const [isLoading, setIsLoading] = useState(false);
const [hasError, setHasError] = useState(false);

Такая модель позволяет получить противоречивые комбинации и разрозненные
обновления: например, `isLoading = true` вместе с `data !== null` или
`hasError = true` без описания самой ошибки.

Если состояние содержит несколько связанных полей и переходы между ними
происходят в ответ на события, объединить их в один `useReducer`. Редюсер
должен менять связанные данные и их флаги в рамках одного перехода:

type State =
    | { status: "idle" }
    | { status: "loading" }
    | { status: "success"; data: Data }
    | { status: "error"; error: string };

type Action =
    | { type: "load" }
    | { type: "success"; data: Data }
    | { type: "error"; message: string };

const [state, dispatch] = useReducer(reducer, initialState);

В простом случае предпочтительнее discriminated union из пункта 1.2: она
делает невозможные комбинации непредставимыми на уровне типов. `useReducer`
нужен не для любого `useState`, а когда состояние имеет несколько связанных
полей или сложные переходы.

Не объединять в один редюсер независимые состояния только ради уменьшения
количества хуков.

---

## 1.4. Не допускать невозможных состояний

Искать модели наподобие:

{
loading: true,
data: {...},
error: "..."
}

если по бизнес-логике данные варианты не могут существовать одновременно.

При обнаружении предложить сделать невозможное состояние
непредставимым на уровне типов.

---

# 2. Полнота обработки состояний

Если discriminated union обрабатывается через switch,
проверить полноту обработки вариантов.

Предпочтительно использовать assertNever:

export function assertNever(x: never, hint?: string): never {
throw new Error(
`Unhandled variant${hint ? ` in ${hint}` : ""}: ${JSON.stringify(x)}`
);
}

Пример:

switch (state.status) {
case "idle":
...
break;

    case "loading":
        ...
        break;

    case "success":
        ...
        break;

    case "error":
        ...
        break;

    default:
        return assertNever(state);
}

Если добавление нового состояния может пройти незамеченным,
отметить это как проблему типобезопасности.

---

# 3. UI должен зависеть от состояния, а не управлять бизнес-логикой

Проверять компоненты на большое количество условий:

if (loading) ...
if (error) ...
if (data) ...
if (!data && !loading) ...

Если эти условия описывают одну state machine,
предложить единое состояние и явное ветвление:

switch (state.status) {
case "loading":
return <Loader />;

    case "error":
        return <ErrorState />;

    case "success":
        return <Content data={state.data} />;

    ...
}

Не требовать switch, если простое условие читается лучше.

---

## 3.1. Компоненты должны оставаться чистыми

Компонент должен в первую очередь описывать отображение: принимать `props`,
получать состояние из хуков и возвращать JSX. Основную бизнес-логику,
запросы к API, подписки, таймеры, преобразование данных и сложные переходы
состояния следует выносить в custom hooks или функции соответствующего
домена.

Плохо, когда компонент одновременно:

- управляет несколькими связанными флагами и данными;
- выполняет запросы и обрабатывает все варианты ответа;
- содержит `useEffect` для подписок, таймеров или синхронизации;
- реализует бизнес-правила прямо внутри JSX.

Предпочтительно:

const { state, actions } = useUserData(userId);

return <UserView state={state} onRetry={actions.retry} />;

Такой подход упрощает чтение компонента, позволяет отдельно тестировать
логику и явно разделяет отображение и побочные эффекты.

Не считать нарушением простые UI-условия, обработчики событий, локальное
состояние отображения и небольшие преобразования, необходимые только для
рендера. Не выносить уникальную однострочную логику в hook формально.

---

# 4. Shared-код

Проверить директории:

shared/
shared/lib/
shared/hooks/
shared/utils/

В shared разрешено помещать только действительно
переиспользуемый и доменно-независимый код.

---

# 5. Форматтеры

Общие функции форматирования должны быть вынесены
в тематические модули.

Предпочтительно:

shared/lib/format/
date.ts
price.ts
pluralize.ts

или аналогичная структура проекта.

Примеры допустимых функций:

formatPrice(...)
formatDate(...)
pluralize(...)

Не складывать все функции в один абстрактный:

utils.ts

если функции относятся к разным областям.

Проверять наличие больших `utils.ts` / `helpers.ts`
со слабо связанными функциями.

---

# 6. Helpers

Допустимы небольшие универсальные функции,
которые не зависят от бизнес-домена.

Например:

assertNever(...)
sleep(...)
clamp(...)

Но helper должен действительно быть универсальным.

Следующие функции обычно НЕ должны находиться в shared:

formatTaskStatus(...)
getUserAvatarUrl(...)
getProductQueueStatus(...)

если они знают о конкретных сущностях проекта.

Такие функции должны находиться ближе к соответствующей сущности,
feature или domain-модулю.

---

# 7. Проверка доменной зависимости shared

Для каждого файла shared проверить:

"Можно ли перенести этот файл в совершенно другой проект,
не перенося вместе с ним бизнес-сущности текущего приложения?"

Если нет — возможно, код находится не на своем архитектурном уровне.

Не считать это абсолютным правилом.
Учитывать существующую архитектуру проекта.

---

# 8. Custom Hooks

Искать повторяемую React-логику,
которая используется минимум в нескольких местах:

- таймеры;
- countdown;
- подписки;
- SSE/WebSocket;
- listeners;
- resize;
- localStorage synchronization;
- polling;
- обработка visibility;
- debounce/throttle с lifecycle.

Если одинаковая stateful-логика используется в 2+ местах,
рассмотреть вынос в custom hook.

Пример:

useCountdown(...)
useEventSource(...)
useWindowSize(...)

Не выносить однострочную или уникальную логику в hook
ради формального переиспользования.

---

# 9. Проверка useEffect

Для каждого useEffect проверить:

1. Нужен ли effect вообще.
2. Есть ли внешняя система, которую он синхронизирует:
    - таймер;
    - DOM API;
    - подписка;
    - сеть;
    - EventSource;
    - WebSocket;
    - browser API.
3. Корректны ли dependencies.
4. Есть ли cleanup, если создается внешний ресурс.

Особенно проверять:

setInterval
setTimeout
addEventListener
EventSource
WebSocket
subscribe

---

# 10. Очистка ресурсов

Если effect создает ресурс:

const id = setInterval(...)

должна быть очистка:

return () => clearInterval(id);

Если:

window.addEventListener(...)

должно быть:

return () => window.removeEventListener(...);

Если:

const source = new EventSource(...)

должно быть закрытие соединения:

return () => source.close();

Отсутствие cleanup считать потенциальной утечкой ресурса.

React прямо рекомендует cleanup для эффектов, которые создают
подписки, соединения или таймеры. 

# 11. Таймеры

Для countdown-таймеров проверить:

- время считается от абсолютного deadline;
- не происходит накопления ошибки через `state - 1000`;
- значение не становится отрицательным;
- таймер автоматически прекращает работу после истечения;
- interval очищается при unmount;
- изменение deadline корректно пересоздает таймер.

Предпочтительный подход:

const ms = Math.max(0, deadline - Date.now());

а не:

setRemaining((value) => value - 1000);

---

# 12. Не создавать универсальные функции "на все случаи"

Искать функции:

function format(value, type, options, mode, ...)

с большим количеством:

if
switch
boolean parameters
mode parameters

Если функция фактически выполняет несколько разных операций,
предложить разделение:

formatPrice(...)
formatDate(...)
formatPercent(...)

вместо:

format(value, "price")
format(value, "date")

Применять это правило только когда разделение действительно
улучшает cohesion и читаемость.

---

# 13. Избегать boolean-параметров режима

Проверять конструкции:

someFunction(value, true)
someFunction(value, false)

или:

function parse(value, isShort, isRussian, includeSeconds)

если параметры меняют фундаментальное поведение функции.

Предпочитать:

formatShortDate(...)
formatFullDate(...)

или объект параметров, если это действительно одна операция.

---

# 14. Дублирование

Искать повторяющийся код.

Перед рекомендацией вынести его в shared проверить:

1. Код действительно одинаков по смыслу?
2. Он относится к одной абстракции?
3. Вероятно ли совместное изменение?
4. Не относится ли он к разным доменам случайно?

Не применять DRY механически.

Два похожих блока кода могут остаться отдельными,
если они имеют разную бизнес-причину для изменения.

---

# 15. Архитектурное расположение

Проект следует организовывать по Feature-Sliced Design (FSD). При проверке
учитывать назначение слоёв и направленность зависимостей:

app
инициализация приложения, провайдеры, глобальные стили и маршрутизация

pages
композиция страниц из widgets, features и entities

widgets
самостоятельные крупные UI-блоки

features
пользовательские действия и бизнес-сценарии

entities
модели и представление конкретных бизнес-сущностей

shared
переиспользуемый доменно-независимый код

Верхний слой может импортировать нижний, но нижний не должен зависеть от
верхнего. Не создавать прямые зависимости между слайсами одного слоя без
необходимости. Публичный API слайса должен быть явным: внешние модули
импортируют его через `index.ts`, а не из внутренних файлов.

При обнаружении reusable-кода определить правильный уровень:

shared
универсальный код без знания бизнеса

entities
логика конкретной бизнес-сущности

features
пользовательское действие / бизнес-сценарий

widgets
крупная композиция UI

pages
композиция страницы

app
инициализация приложения

Не переносить бизнес-функции в shared только потому,
что ими пользуются несколько компонентов.

---

# 16. Один компонент в одном файле

В одном файле должен находиться один React-компонент. Это упрощает навигацию,
поиск, изоляцию изменений и поддержание публичного API модуля.

Не считать нарушением небольшие приватные подкомпоненты, которые нужны только
родительскому компоненту и не имеют самостоятельной ответственности. Если
подкомпонент содержит собственную логику, состояние, стили или может
использоваться отдельно, вынести его в отдельный файл.

Не включать в это правило TypeScript-типы, константы, custom hooks и обычные
вспомогательные функции, относящиеся к основному компоненту.

---

# 17. Приоритет нарушений

Для каждого найденного нарушения назначить уровень.

CRITICAL
- возможная ошибка выполнения;
- утечка соединения;
- неправильное состояние приложения;
- нарушение бизнес-логики.

HIGH
- невозможные состояния;
- отсутствие exhaustiveness checking для важной state machine;
- неправильный lifecycle SSE/WebSocket;
- серьезное нарушение архитектурных границ.

MEDIUM
- дублирование stateful-логики;
- слишком универсальный helper;
- доменная функция в shared;
- сложный набор флагов.

LOW
- нейминг;
- организация formatter/helper;
- небольшой архитектурный smell без практических последствий.

---

# 18. Что НЕ считать нарушением автоматически

Не считать ошибкой:

- любой boolean state;
- любой useEffect;
- отсутствие custom hook для единичной логики;
- наличие helper-файла;
- два похожих фрагмента кода;
- switch без assertNever, если union не используется;
- локальную функцию, которую теоретически можно вынести;
- код, который не соответствует личным stylistic preferences.

Аргументировать каждое замечание конкретным риском.

---

# 19. Формат результата

В начале дать итог:

Code review summary

Critical: N
High: N
Medium: N
Low: N

Затем нарушения.

Пример:

### HIGH — состояние запроса представлено независимыми флагами

Файл:
src/features/product/model/useProduct.ts

Код:

const [loading, setLoading] = useState(false);
const [data, setData] = useState<Product | null>(null);
const [error, setError] = useState<string | null>(null);

Проблема:

Эти значения описывают одну state machine и допускают
невозможные комбинации, например одновременно data + error.

Рекомендация:

Использовать discriminated union:

type ProductState =
| { status: "idle" }
| { status: "loading" }
| { status: "success"; data: Product }
| { status: "error"; error: string };

---

Если серьезных нарушений нет:

"Нарушений требований не обнаружено."

Не придумывать замечания только для заполнения отчета.
