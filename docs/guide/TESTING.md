# Критерии приёмки — Trade Chain

Ручные тест-кейсы для проверки задеплоенного стенда. Каждый кейс: шаги и
ожидаемый результат. Документ содержит 29 ручных кейсов; сервисные правила
обмена дополнительно покрыты автоматическими тестами backend.

## Предусловия

- Фронт: **https://tvchbmen-front.vercel.app**
- API: **https://tvchbmen-api.vercel.app** (фронт ходит в него через прокси
  `/api/v1`, отдельно дёргать не обязательно)
- База засеяна демо-данными: 15 пользователей, 18 товаров, 8 категорий,
  готовая цепочка обмена (RTX 4080 → MacBook Pro → велосипед → iPhone → …).
- Пароли засеянных пользователей неизвестны намеренно — во всех кейсах с
  входом **регистрируем нового пользователя**. Каталог и поиск доступны без
  входа.

Проверять можно двумя способами:

- **через UI** — по шагам в браузере;
- **через API** — `curl`/Postman по `https://tvchbmen-api.vercel.app`. Для
  защищённых маршрутов сначала получить токен (кейс TC-03) и слать заголовок
  `Authorization: Bearer <token>`.

Формат ошибок API: `{"error":"..."}`. Отсутствие/невалидность токена —
`401` текстом, без JSON.

## 1. Каталог и категории (без входа)

### TC-01. Каталог товаров открывается
**Шаги.** Открыть главную страницу фронта. (API: `GET /api/v1/products`.)
**Ожидаемо.** Страница отдаёт `200`, показан список товаров (≥ 18 из сида):
RTX 4080, MacBook Pro, iPhone и т.д.

### TC-02. Список категорий
**Шаги.** `GET /api/v1/categories`.
**Ожидаемо.** `200`, 8 категорий: Велосипед, Видеокарта, Игровая приставка,
Ноутбук, Планшет, Телефон, Фотоаппарат, Часы.

### TC-02a. Карточка товара по id
**Шаги.** Взять `product_id` любого товара из TC-01, открыть карточку.
(API: `GET /api/v1/products/{id}`.)
**Ожидаемо.** `200`, детали товара. Для несуществующего UUID — `404`
`{"error":"resource not found"}`.

### TC-02b. Текстовый поиск товаров
**Шаги.** `GET /api/v1/products/search?q=iPhone`.
**Ожидаемо.** `200`, только совпадения (iPhone 13, iPhone 15). Без `q` —
`400 invalid input`.

## 2. Регистрация и вход

### TC-03. Регистрация нового пользователя
**Шаги.** Зарегистрироваться с уникальным email и паролем (например
`alice+<время>@test.local` / `secret123`).
(API: `POST /api/v1/auth/register`, тело `{"email","password"}`.)
**Ожидаемо.** `201`, в ответе `token` и объект пользователя. Токен сохранить
для следующих кейсов.

### TC-04. Повторная регистрация того же email
**Шаги.** Повторить TC-03 с тем же email.
**Ожидаемо.** `409` — пользователь уже существует.

### TC-05. Вход с верным паролем
**Шаги.** `POST /api/v1/auth/login` с данными из TC-03.
**Ожидаемо.** `200`, свежий `token`.

### TC-06. Вход с неверным паролем
**Шаги.** Тот же email, другой пароль.
**Ожидаемо.** `400` — неверный email или пароль. Токен не выдаётся.

---

## 3. Товары (нужен токен)

### TC-07. Создание товара без токена запрещено
**Шаги.** `POST /api/v1/products` без заголовка `Authorization`.
**Ожидаемо.** `401`.

### TC-08. Создание своего товара
**Шаги.** С токеном из TC-03 отправить `POST /api/v1/products`:
`{"customer_id":"<свой id>","category_id":"<любая категория>","title":"Гитара","price":40000,"location":"Москва","status":"active"}`.
**Ожидаемо.** `201`, вернулся товар с `product_id`.

### TC-09. Список своих товаров
**Шаги.** `GET /api/v1/products/by-customer/{customerID}` со своим id.
**Ожидаемо.** `200`, среди товаров — созданный в TC-08.

---

## 4. Предложения обмена (нужен токен)

Для блока нужны **двое**: пользователь A и пользователь B, у каждого свой
товар (по TC-03 и TC-08). Товар A — `pA`, товар B — `pB`.

### TC-10. Список предложений без токена запрещён
**Шаги.** `GET /api/v1/exchange-offers` без токена.
**Ожидаемо.** `401`.
> Регресс-маркер: раньше здесь был `404` — маршруты обмена были отключены.
> `401` подтверждает, что фикс роутера доехал.

### TC-11. Неизвестные фильтры отклоняются
**Шаги.** `GET /api/v1/exchange-offers?role=both` и `?status=whatever`
(с токеном).
**Ожидаемо.** оба — `400`, а не молча урезанный список.

### TC-12. A отправляет предложение B
**Шаги.** Токеном A: `POST /api/v1/exchange-offers`
`{"offered_product_id":"pA","requested_product_id":"pB","comment":"Меняюсь"}`.
**Ожидаемо.** `201`, в ответе `id`, `status:"pending"`, `conversation_id == id`.

### TC-13. Дубль предложения блокируется
**Шаги.** Повторить TC-12 тем же токеном по той же паре, пока первое ждёт
ответа.
**Ожидаемо.** `409` — уникальный индекс не даёт близнеца.

### TC-14. Предложение самому себе отклоняется
**Шаги.** Токеном A: предложить обмен `pA` на `pA`.
**Ожидаемо.** `400` (или `403/409`) — товары должны принадлежать разным
людям.

### TC-15. Нулевая доплата с плательщиком отклоняется
**Шаги.** Токеном B: предложение с `surcharge:{amount:0,currency:"RUB",payer:"<id B>"}`.
**Ожидаемо.** `400` — нулевая доплата с указанным плательщиком не имеет
смысла.

### TC-16. Списки входящих/исходящих
**Шаги.** `GET /api/v1/exchange-offers?role=outgoing` токеном A и
`?role=incoming` токеном B.
**Ожидаемо.** оба `200`; предложение из TC-12 видно у A как исходящее, у B
как входящее.

### TC-17. Детали предложения
**Шаги.** `GET /api/v1/exchange-offers/{offerID}` токеном B.
**Ожидаемо.** `200`, детали и состояние.

### TC-18. Чужой не видит предложение
**Шаги.** Зарегистрировать третьего (C) и открыть детали чужого предложения
его токеном.
**Ожидаемо.** `403` (или `404`) — доступ только у сторон обмена.

### TC-19. Автор не может принять своё предложение
**Шаги.** Токеном A вызвать `POST /api/v1/exchange-offers/{offerID}/accept`.
**Ожидаемо.** `403` (или `400/409`) — принимает только получатель.

## 5. Приём и завершение обмена

### TC-20. B принимает предложение
**Шаги.** Токеном B: `POST /api/v1/exchange-offers/{offerID}/accept`.
**Ожидаемо.** `200`, статус `accepted`.

### TC-20a. Нельзя принять предложение с недоступным товаром
**Шаги.** Создать новое предложение по TC-12, затем до его принятия перевести
один из товаров в статус `exchanged` завершением другого обмена. Токеном
получателя вызвать `POST /api/v1/exchange-offers/{offerID}/accept`.
**Ожидаемо.** Ошибка конфликта (`409`), исходное предложение остаётся
`pending`, владельцы и статус недоступного товара не откатываются.

### TC-21. Неизвестный итог подтверждения отклоняется
**Шаги.** `POST /api/v1/exchanges/{offerID}/confirm` с `{"result":"maybe"}`.
**Ожидаемо.** `400`.

### TC-22. Двойное подтверждение завершает обмен
**Шаги.** Токеном A: `confirm {"result":"success"}` → затем токеном B:
`confirm {"result":"success"}`.
**Ожидаемо.** после A — статус `awaiting_recipient`; после B — `completed`.

### TC-23. Товары сменили владельцев
**Шаги.** `GET /api/v1/products/{pA}` и `/{pB}`.
**Ожидаемо.** `pA` теперь принадлежит B, `pB` — A.

### TC-24. Провал обмена по одной стороне
**Шаги.** Собрать новое принятое предложение (TC-12, TC-20) и один раз
вызвать `confirm {"result":"failed","reason":"Не договорились"}`.
**Ожидаемо.** `200`; обмен помечен неуспешным без согласия второй стороны,
владельцы не меняются.

### TC-24a. Завершение закрывает конкурирующие предложения
**Шаги.** Создать два предложения, использующие один и тот же товар, принять
одно из них и завершить его двумя успешными подтверждениями.
**Ожидаемо.** Завершённое предложение получает `completed`; конкурирующее
исходящее предложение получает `cancelled`, а входящее предложение по уже
занятому товару — `unavailable`. Оба товара получают статус `exchanged`.

## 6. Поиск цепочки обмена

### TC-25. Поиск цепочки без токена запрещён
**Шаги.** `GET /api/v1/search/chain?target_product_id=<любой>` без токена.
**Ожидаемо.** `401`.

### TC-26. Поиск строит путь к цели
**Шаги.** Войти, иметь хотя бы один свой активный товар. Запросить
`GET /api/v1/search/chain?target_product_id=<id RTX 4080>&max_depth=6`.
**Ожидаемо.** `200`, `{"chain":[...],"length":N}` — путь от своего товара к
цели.

### TC-27. Нет пути — пустой ответ, не ошибка
**Шаги.** Запросить цепочку к товару, до которого пути нет.
**Ожидаемо.** `200` `{"chain":[],"length":0}`.
> Регресс-маркер: раньше здесь падала `500` (nil-паника в хендлере).

### TC-28. Некорректная глубина
**Шаги.** `...&max_depth=0`.
**Ожидаемо.** `400` — глубина должна быть больше нуля.

### TC-29. У пользователя нет товаров
**Шаги.** Свежий пользователь без товаров запрашивает поиск цепочки.
**Ожидаемо.** `400` (не `500`) — меняться нечем.

## 7. Сводка маршрутов и кодов

| Маршрут | Без токена | Валидный запрос | Ошибка ввода |
| --- | --- | --- | --- |
| `POST /auth/register` | 201 | 201 | 409 (дубль) |
| `POST /auth/login` | 200 | 200 | 400 (неверный пароль) |
| `GET /products` | 200 | 200 | — |
| `GET /products/search` | 200 | 200 | 400 (без `q`) |
| `GET /products/{id}` | 200 | 200 | 404 |
| `POST /products` | 401 | 201 | 400 |
| `GET /exchange-offers` | 401 | 200 | 400 (фильтры) |
| `POST /exchange-offers` | 401 | 201 | 400 / 409 |
| `POST /exchange-offers/{id}/accept` | 401 | 200 | 403 (не сторона) |
| `POST /exchanges/{id}/confirm` | 401 | 200 | 400 (итог) |
| `GET /search/chain` | 401 | 200 | 400 (`max_depth<=0`) |

## 8. Автоматические тесты backend

Запустить все автоматические тесты:

```bash
cd back
go test ./...
```

Сервисные тесты в `../../back/internal/service/chain_test.go` дополнительно
проверяют:

- создание предложения со статусом `pending` и сохранение получателя;
- запрет предложения чужого товара и принятия предложения инициатором;
- завершение только после подтверждений обеих сторон;
- немедленный переход в `failed` после отрицательного подтверждения;
- смену владельцев и перевод товаров в `exchanged`;
- закрытие конкурирующих `pending` и `active` предложений;
- отказ в принятии предложения с уже недоступным товаром;
- повторные подтверждения, действия посторонних пользователей и неизвестные действия;
- доступ к переписке только участникам и возможность оставить отзыв только после завершённого обмена.

## Приёмка пройдена, если

- Все кейсы TC-01…TC-29 дают ожидаемый результат.
- Автоматическая команда `go test ./...` завершается без ошибок.
- Ни один сценарий не отвечает `500`.
- Сквозной обмен (TC-12 → TC-23) реально переносит владельцев товаров.
