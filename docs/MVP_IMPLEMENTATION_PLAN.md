## Этап 1. Контекст маршрута в форме предложения (P0, уязвимость 9.8)

**Зачем.** Пока форма всегда шлёт голый `from_product_id → to_product_id`, любое предложение из ленты и из карточки-кандидата создаёт самостоятельную цепочку, и обещание «цель сохраняется» технически не выполняется.

**Файлы**

- `front/src/features/exchange/ui/useOfferExchangeForm.ts`
- `front/src/features/exchange/ui/OfferExchangeModal.tsx`
- `front/src/features/exchange/ui/offer-exchange-modal.module.css`
- `front/src/features/exchange/lib/useMyGoals.ts` — новый
- вызывающие: `pages/product/ui/ProductPage.tsx`, `pages/route/ui/RoutePage.tsx`, новая лента

**Что делаю**

1. Добавляю в пропсы модалки необязательный `routeContext?: { exchangeGoalId?: string; routeStepId?: string; previousChainId?: string; goalTitle?: string }`.
2. В `useOfferExchangeForm` расширяю тело `createChain` этими полями (типы `TCreateChainRequest` их уже содержат — правки контракта не требуется).
3. Новый хук `useMyGoals`: из `useGetMyChainsQuery` собирает активные цели пользователя (группировка по `exchange_goal_id`/`to_category_id`, статусы `pending`/`active`), отдаёт `{ goalId, goalTitle, currentProductId, previousChainId, activeOffersCount }`.
4. В форме — блок «Куда засчитать обмен» с radio: «Отдельный обмен» / список активных маршрутов. Если `routeContext` пришёл извне (переход из «Пути к цели»), маршрут выбран заранее и показывается карточкой «Цель → Сейчас у вас», как требует 9.1.
5. `useRoute.submitSelectedOffers` перевожу на тот же сборщик payload, чтобы логика связывания жила в одном месте.

**Готово, когда**: предложение, отправленное из карточки товара при выбранном маршруте, приходит в `POST /chains` с `exchange_goal_id` и `route_step_id`, появляется в истории маршрута на `/route`, а не отдельной цепочкой в общем списке.

## Этап 2. Переключатель «Лента / Сетка» (P0)

**Зачем.** Точка входа в оба представления и требование «выбранный режим не сбрасывается» (Шаг 2).

**Файлы**

- `front/src/shared/ui/viewModeToggle/` — новый компонент (`ViewModeToggle.tsx`, `.module.css`, `.stories.tsx`, `index.ts`)
- `front/src/pages/catalog/lib/useCatalogViewMode.ts` — новый
- `front/src/pages/catalog/ui/CatalogPage.tsx`

**Что делаю**

1. `ViewModeToggle` — сегментированный контрол на двух кнопках с `role="radiogroup"`, иконка+подпись, `aria-checked`, focus-visible по токенам. Существующий `Switcher` не подходит: он булев чекбокс с треком, а нужен именно выбор из двух равноправных режимов.
2. `useCatalogViewMode`: источник правды — query-параметр `?view=feed|grid`, при монтировании подхватывает `localStorage['catalog-view-mode']`, при смене пишет обратно. Query-параметр нужен, чтобы ссылка на ленту делилась и переживала перезагрузку; localStorage — чтобы «последний выбор сохранялся» между сессиями.
3. `CatalogPage` рендерит переключатель в `PageHeader.actions` и по режиму отдаёт либо текущую сетку, либо `ProductFeed`.

**Готово, когда**: переключение не теряет `q` и `category_id`, выбранный режим восстанавливается после перезагрузки и после возврата с карточки товара.

## Этап 3. Вертикальная лента товаров (P0)

**Зачем.** Раздел 2.2 и оба фото-референса: полноэкранная карточка, вертикальная прокрутка, вертикальный столбец действий справа, подпись автора снизу; на desktop — медиа слева, панель с описанием и действиями справа.

**Файлы**

- `front/src/widgets/productFeed/` — новый виджет: `ProductFeed.tsx`, `FeedItem.tsx`, `FeedActions.tsx`, `useProductFeed.ts`, `product-feed.module.css`, `feed-item.module.css`, `*.stories.tsx`, `index.ts`
- `front/src/shared/lib/useSwipeGesture.ts` — перенос из `features/routeRecommendations/ui/`, реэкспорт с прежнего места, чтобы не трогать карусель рекомендаций
- `front/src/pages/catalog/ui/CatalogPage.tsx`, `catalog-page.module.css`

**Что делаю**

1. **Данные — те же.** Лента получает `products`, `hasMore`, `loadMoreRef`, `isFetching` из существующего `useCatalog`. Никакого второго запроса и никакой отдельной механики обмена: это требование 9.2.
2. **Прокрутка.** CSS scroll-snap (`scroll-snap-type: y mandatory`, `scroll-snap-align: start`) на контейнере с `height: calc(100dvh - var(--header-height))`. Догрузка — тот же `IntersectionObserver` через `loadMoreRef`, помещённый последним элементом ленты.
3. **Мобильная раскладка** (референс 1): изображение на весь экран с `object-fit: cover`, поверх — градиентный оверлей снизу (допустим по AGENTS.md), слева внизу автор + название + «Хочу взамен» с раскрытием «Ещё», справа вертикальный столбец действий.
4. **Desktop-раскладка** (референс 2): grid `1fr 380px` — медиа слева, справа панель с названием, описанием, категорией, городом, владельцем (`SellerInfo`), желаемыми категориями и кнопками. Ниже `768px` — переключение на мобильную раскладку.
5. **Действия** (`FeedActions`), все ведут в уже существующие сценарии:
   - «Предложить обмен» — открывает `OfferExchangeModal` с `routeContext`, если лента открыта под цель (`?goal=<id>`);
   - «Найти путь» — `/route?target=<id>`;
   - «Открыть товар» — `/product/:id`;
   - «В вишлист» — существующий `@features/wishlist`;
   - «Профиль владельца» — `/profile/:customerId`.
   Жесты только переключают карточки; лайк/обмен жестом не вешаю — прямой запрет из 2.2.
6. **Клавиатура и доступность**: `↑`/`↓`/`PageUp`/`PageDown` листают, каждая карточка — `<article>` с `aria-label`, действия — обычные кнопки в табпорядке, `@media (prefers-reduced-motion: reduce)` отключает плавный скролл.
7. **Метка «Вам подойдёт»** из сетки переносится в ленту бейджем на карточке (`product.matched`) — иначе объяснение «почему мне это показали» теряется при переключении режима.

**Готово, когда**: лента листается свайпом, колесом и клавиатурой; догружает страницы; из неё отправляется предложение, которое видно во вкладке «Обмены»; на desktop и mobile нет горизонтального переполнения.

**Готово, когда**: сценарий жюри пункт 3 проходит без единого выхода из контекста цели.

3. В шапке и в профиле — «Сменить аккаунт» (возврат на `/demo`).

**Уточнение, которое приму сам, если не поступит других указаний**: сброс реализую как «полный откат к сиду» (все обмены/сообщения/подтверждения демо-пользователей), а не выборочный по одному профилю — выборочный сброс не защищает от порчи состояния соседями, ради чего пункт 9.7 и написан.

### Осталось

1. **Этап 6, объяснимость (P1)**: пояснения на карточках рекомендаций («2 шага до цели», «тот же город», «разница стоимости») и группировка конкурирующих предложений внутри карточки цели со счётчиком. Данные для этого уже есть в `groupChainsByGoal` и `useRoute`.
2. **Storybook для новых компонентов**: стори написаны только для `ViewModeToggle`; для `ProductFeed`, `QuickProductForm` и `RequiredAction` — нет.
3. **Демо-роли в mock-api**: `front/mock-api/data.js` — независимый от Postgres набор данных, миграция `013` его не касается. При показе на mock-api состояния пяти профилей не совпадут с подписями на `/demo`.
4. **Сквозной прогон сценария жюри на реальном бэкенде**: проверено на mock-api (лента, предложение из ленты, вход под демо-профилем, «От вас требуется»). Полный путь из раздела 12 с двумя аккаунтами и подтверждением обмена на поднятом Postgres не прогонялся.

### Замечания, найденные попутно

- `back/internal/service/chain_test.go` не компилировался с коммита `4fc5cf1`: у `TestSingleNegativeConfirmationFailsExchange` был лишний параметр, из-за чего падал весь пакет `internal/service`. Починено (параметр убран, вместо него используется `initiator`) — иначе `go test ./...` не проходил.
- В `docker-compose.yml` не были смонтированы миграции `009` и `012`, хотя они существуют. Добавлен `012` (иконки категорий) и новый `013`. `009_prevent_archived_product_reactivation.sql` намеренно не трогал — не проверял, безопасно ли включать его в существующие стенды.

## Границы работ

- Логика обменов, статусы, правила согласования и алгоритм подбора не меняются (ограничение задачи из раздела 1).
- Модель товара остаётся с одним изображением — множественные фото и видео в ленте вне объёма (P2).
- Из бэкенда трогаю только демо-обвязку: миграция с данными профилей и эндпоинт сброса.
