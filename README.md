# Trade Chain

## Описание проекта

**Trade Chain** — веб-приложение для размещения объявлений о товарах и поиска цепочек обмена между пользователями.

Пользователь может:

- зарегистрироваться и авторизоваться;
- создавать объявления о товарах;
- указывать категорию, описание, стоимость и местоположение товара;
- добавлять изображения;
- указывать желаемые товары для обмена;
- просматривать каталог объявлений;
- искать товары по названию и описанию;
- фильтровать объявления по категориям;
- находить цепочки обменов между товарами разных пользователей;
- управлять собственными объявлениями.

Поиск цепочек обмена позволяет построить последовательность обменов, в которой каждый следующий пользователь предлагает товар, необходимый предыдущему участнику цепочки.

Все основные операции с приложением выполняются через веб-интерфейс.

## Реализованный дополнительный функционал

Базовый MVP позволяет найти путь к желаемому товару и отправить предложение обмена. Поверх этого сценария реализованы функции, которые помогают пользователю быстрее выбрать подходящий шаг, не пропустить действия второй стороны и безопасно завершить сделку.

### Frontend

- **Контекстный подбор на карточке товара.** Интерфейс сопоставляет пожелания владельца объявления с активными товарами текущего пользователя и сразу показывает подходящие варианты прямого обмена. Параллельно рядом отображается возможный путь через цепочку.
- **Несколько предложений с частичным успехом.** Пользователь может выбрать несколько вариантов следующего обмена. Каждое предложение отправляется независимо, поэтому ошибка одного запроса не отменяет успешно созданные предложения.
- **Центр уведомлений.** Отдельная лента показывает новые предложения, сообщения и изменения состояния сделки, хранит отметки о прочтении и позволяет перейти из уведомления прямо в нужный обмен.
- **Персональные интересы.** В профиле можно указать интересующие категории и изменять их независимо от пожеланий к конкретному товару.
- **Устойчивый и адаптивный маршрут.** Стартовый товар и цель сохраняются в URL, а desktop-сценарий выбора на мобильном превращается в последовательные шаги с просмотром рекомендаций свайпами.

### Backend

- **Ранжирование следующего обмена.** API отдельно выдаёт прямые совпадения и кандидатов для продолжения пути, отдавая приоритет товарам, которые соответствуют явно указанным пожеланиям участников.
- **События в реальном времени.** Авторизованная SSE-подписка сообщает об изменениях сделки и новых сообщениях без постоянного опроса API. Между экземплярами backend события распространяются через PostgreSQL `LISTEN/NOTIFY`.
- **Состояние уведомлений.** Backend хранит отметки о прочтении, поддерживает чтение одного события и всех уведомлений и проверяет, что пользователь действительно участвует в соответствующем обмене.
- **Переговоры и условия сделки.** В обмен встроены чат, комментарий к предложению, доплата с указанием плательщика и валюты, а также автоматическое истечение предложения через 72 часа.
- **Безопасное завершение.** Сделка завершается только после подтверждения обеими сторонами. Передача товаров выполняется транзакционно, а отзыв можно оставить только после состоявшегося обмена.

## Ограничения MVP

### Продуктовые ограничения

- Цепочка является навигатором по независимым двусторонним обменам, а не атомарной сделкой между всеми участниками. Отказ на одном шаге не отменяет уже завершённые обмены: сервис сохраняет цель и предлагает продолжить путь другим способом.
- Сервис помогает согласовать обмен, но не проводит оплату и доставку. Доплата хранится как условие договорённости между пользователями и не является платёжной операцией.
- У товара хранится одно изображение. Галерея из нескольких фотографий и видео не входят в текущий MVP.
- В рекомендациях пока нет подробного объяснения ранжирования и группировки конкурирующих предложений по одной цели.
- Демонстрационный вход предназначен только для учебного стенда и по умолчанию включён в Docker Compose. В production его необходимо отключать через `DEMO_LOGIN_ENABLED=false`.

### Технические ограничения

- Максимальная глубина маршрута задаётся параметром `max_depth`; значение по умолчанию — `10`. Отсутствие пути является штатным результатом и возвращается как пустая цепочка.
- Автоматический перевод просроченных предложений в итоговый статус требует защищённого cron-вызова и настройки `CRON_SECRET`. Даже без cron просроченное предложение не считается активным при чтении через API.
- Сброс демонстрационных данных недоступен, пока не задан `DEMO_RESET_SECRET`; это защищает стенд от случайного удаления всех обменов.
- Mock API использует отдельный набор данных и упрощённые токены, поэтому подготовленные состояния пяти демо-профилей следует проверять на Docker-стенде с PostgreSQL.

## Запуск проекта

### Требования

Для запуска проекта необходимы:

- Docker
- Docker Compose

### Запуск

Перед запуском задайте `JWT_SECRET` длиной не менее 32 символов в файле `.env`:

```bash
cp .env.example .env
```

Замените значение `JWT_SECRET` в `.env` на собственный секрет. Не добавляйте
`.env` в Git.

Запуск выполняется одной командой:

```bash
docker compose up --build
```

После запуска:

- **Frontend:** http://localhost:3000
- **Backend API:** http://localhost:8080
- **Проверка backend:** http://localhost:8080/health
- **Swagger UI:** http://localhost:8080/swagger/index.html
- **PostgreSQL:** `localhost:5432`

### Самостоятельная проверка

Убедитесь, что backend отвечает:

```bash
curl -fsS http://localhost:8080/health
```

Ожидаемый ответ:

```json
{ "status": "ok" }
```

Затем откройте `http://localhost:3000/demo` и проверьте два подготовленных сценария:

1. Выберите профиль **«Искатель»** — в нём есть два активных товара. Выберите свой товар и цель, после чего интерфейс должен показать прямые варианты или маршрут следующего обмена.
2. Выберите профиль **«Получатель»** — в нём уже есть входящее предложение. Откройте его, примите или отклоните и убедитесь, что состояние сделки и требуемое действие изменились.

Если интерфейс, `/health` и оба сценария доступны, основной MVP запущен корректно. Дополнительные ручные проверки приведены в [docs/guide/TESTING.md](docs/guide/TESTING.md).

### Полный сброс

Для полной остановки проекта и удаления данных PostgreSQL:

```bash
docker compose down -v
```

После сброса проект можно запустить заново:

```bash
docker compose up --build
```

При запуске PostgreSQL автоматически выполняет SQL-файлы из:

```text
back/infrastructure/migrations/
```

Таким образом, структура базы данных и тестовые данные создаются автоматически.

## HTTP API

Базовый URL прикладного API после локального запуска — `http://localhost:8080/api/v1`. Защищённые маршруты принимают JWT в заголовке `Authorization: Bearer <token>`.

| Группа      | Основные маршруты                                               | Назначение                                    |
| ----------- | --------------------------------------------------------------- | --------------------------------------------- |
| Авторизация | `/auth/register`, `/auth/login`, `/auth/me`, `/auth/demo-login` | Регистрация, вход и текущая сессия            |
| Каталог     | `/products`, `/categories`, `/customers`                        | Товары, категории и профили                   |
| Поиск пути  | `/search/chain`, `/search/candidates`                           | Маршрут к цели и следующий обмен              |
| Предложения | `/exchange-offers`, `/exchanges/{id}/confirm`                   | Создание, согласование и подтверждение обмена |
| Переговоры  | `/chains/{id}/messages`                                         | Чат участников сделки                         |
| Уведомления | `/notifications/*`, `/events`                                   | Статусы прочтения и SSE-события               |
| Репутация   | `/reviews/*`                                                    | Отзывы и рейтинг после обмена                 |

- Полное описание запросов и ответов: [docs/guide/API.md](docs/guide/API.md).
- Интерактивная документация: `http://localhost:8080/swagger/index.html`.
- OpenAPI JSON: `http://localhost:8080/swagger/doc.json`.
- Проверка состояния без авторизации: `GET http://localhost:8080/health`.

## Тестирование

### Полная проверка через Docker

Backend можно проверить без локальной установки Go:

```bash
docker compose --profile check run --rm lint
docker compose --profile check run --rm test
```

### Локальные тесты backend

Запустить все тесты backend:

```bash
cd back
go test ./...
```

Сервисные тесты проверяют актуальные правила обменов:

- создание предложения начинается со статуса `pending`, сохраняет получателя и отклоняет предложение чужого товара;
- принять предложение может только получатель, а завершить обмен через смену статуса нельзя;
- обмен завершается только после подтверждений обеих сторон;
- отрицательное подтверждение сразу переводит обмен в `failed`;
- после завершения меняются владельцы товаров, товары получают статус `exchanged`, а конкурирующие предложения переводятся в `cancelled` или `unavailable`;
- предложение нельзя принять после того, как его товар стал недоступен;
- повторное подтверждение, действия постороннего пользователя и неизвестные действия отклоняются;
- переписка доступна только участникам активного обмена, а отзыв — только после завершённого обмена.

Ручные API- и UI-тест-кейсы находятся в [docs/TESTING.md](docs/guide/TESTING.md).

## Особенности реализации

**Цепочка обмена — навигатор, а не многосторонняя сделка.** Система не связывает всех участников в одну хрупкую цепь, которая рассыпается при выходе любого из них. Вместо этого каждый шаг остаётся обычным двусторонним обменом, а сервис ведёт пользователя от текущего товара к цели и пересчитывает маршрут после каждой сделки.

**Поиск маршрута.** Алгоритм обходит граф возможных обменов в ширину (`back/internal/search/bfs.go`), стартуя от целевого товара к товарам текущего пользователя. Глубина поиска ограничена параметром `max_depth`, найденные варианты ранжируются отдельным scorer-компонентом.

**Полнотекстовый поиск.** Товары и категории хранят поисковый вектор `tsvector`, поиск по названию и описанию выполняется средствами PostgreSQL, без внешнего поискового движка.

**Согласование обмена через стейт-машину.** Все переходы статусов предложения и обмена проверяются в отдельном пакете `back/internal/exchange`. Обмен считается состоявшимся только после подтверждения обеими сторонами, а одного отрицательного подтверждения достаточно, чтобы перевести сделку в `failed`.

**Целостность при завершении сделки.** В момент успешного обмена товары блокируются на уровне транзакции, меняют владельцев и получают статус `exchanged`, а конкурирующие предложения по этим товарам автоматически закрываются — товар не может быть обменян дважды.

**Срок жизни предложения.** Предложение живёт 72 часа (`exchange.DefaultTTL`), после чего перестаёт быть активным, чтобы получатель не удерживал чужой товар бесконечно. JWT-токен выдаётся на 24 часа.

**Отзывы защищены от злоупотреблений.** Оставить отзыв можно только по завершённому обмену, поэтому обычный отказ от предложения нельзя превратить в инструмент негативных оценок.

**Опциональная аутентификация каталога.** Каталог доступен без входа, но для авторизованного пользователя из выдачи исключаются его собственные объявления — один и тот же endpoint обслуживает оба случая.

**Feature-Sliced Design на фронтенде.** Код разделён на слои `app`, `pages`, `widgets`, `features`, `entities`, `shared`, что позволило нескольким разработчикам параллельно вести страницы и сценарии без конфликтов.

**Воспроизводимое окружение.** Проект поднимается одной командой: миграции и тестовые данные применяются при первичной инициализации PostgreSQL, а сид-данные генерируются из мок-данных фронтенда скриптом `scripts/generate-mock-seed.mjs` — фронтенд и бэкенд работают на одинаковом наборе данных.

## Аутентификация

Для аутентификации используется **JWT**.

Защищённые endpoints требуют наличия Bearer-токена в HTTP-заголовке:

```text
Authorization: Bearer <token>
```

После проверки токена идентификатор пользователя передаётся через `context` HTTP-запроса.

Каталог объявлений остаётся публичным: неавторизованные пользователи могут просматривать товары.

Для авторизованного пользователя при просмотре каталога его собственные объявления исключаются из результатов.

## База данных

**PostgreSQL** используется как основное постоянное хранилище данных.

PostgreSQL выбран потому, что предметная область содержит связанные сущности
с жёсткими ограничениями целостности: пользователей, товары, желания,
предложения, подтверждения и отзывы. Транзакции и блокировки строк позволяют
безопасно завершать обмен, одновременно менять владельцев товаров и закрывать
конкурирующие предложения, не допуская двойного обмена одной вещи. Встроенный
полнотекстовый поиск через `tsvector` покрывает поиск по объявлениям без
отдельного поискового сервиса, а `pgx` обеспечивает прямую и производительную
интеграцию с Go. PostgreSQL также удобно воспроизводится локально и в CI через
Docker Compose и поддерживается выбранной инфраструктурой деплоя.

Начальная структура базы данных и тестовые данные загружаются через SQL-файлы, расположенные в:

```text
back/infrastructure/migrations/
```

В Docker Compose эта директория подключается к:

```text
/docker-entrypoint-initdb.d
```

PostgreSQL запускает эти SQL-файлы при первичной инициализации базы данных.

## Контейнеризация

Проект полностью запускается через Docker Compose.

Используются три основных контейнера:

| Контейнер           | Назначение       |
| ------------------- | ---------------- |
| `trade-chain-front` | Frontend и Nginx |
| `trade-chain-back`  | Backend          |
| `trade-chain-db`    | PostgreSQL       |

### Backend

Для backend используется многоэтапная сборка Docker-образа.

Сначала Go-приложение компилируется в builder-контейнере, после чего готовый бинарный файл переносится в отдельный runtime-образ.

### Frontend

Frontend также собирается в несколько этапов:

1. Устанавливаются npm-зависимости.
2. Выполняется production-сборка через Vite.
3. Собранные статические файлы передаются в Nginx.
4. Nginx используется для раздачи frontend-приложения.

## Демонстрационные профили

На странице `http://localhost:3000/demo` доступны пять профилей без ввода пароля. Каждый профиль подготовлен для отдельной проверки:

| Профиль            | Подготовленное состояние             | Проверяемый сценарий                                 |
| ------------------ | ------------------------------------ | ---------------------------------------------------- |
| Новый пользователь | Нет товаров и обменов                | Добавление вещи из карточки чужого товара            |
| Искатель           | Два активных товара, обменов нет     | Выбор цели, прямое предложение и построение маршрута |
| Получатель         | Есть входящее предложение            | Принятие или отказ и переход в комнату обмена        |
| В пути             | Есть завершённый шаг и активная цель | Продолжение маршрута с полученным товаром            |
| Опытный участник   | Есть завершённый и отклонённый обмен | История, подтверждение результата и отзывы           |

Профили и тестовые данные создаются автоматически при первой инициализации PostgreSQL. Демонстрационный вход не предназначен для production.

| Показатель             | Значение                  |
| ---------------------- | ------------------------- |

| Коммитов в `dev`       | 217                       |
| Pull request           | 54, из них смержено 45    |
| Веток                  | 23                        |

**Процесс работы с ветками.** Каждая задача велась в отдельной ветке (`feature/...`, `fix/...`, `front-...`), которая попадала в `dev` через pull request. Ветка `main` защищена от прямых коммитов: изменения приходят в неё только из `dev` отдельным pull request. Создание этих pull request автоматизировано workflow-файлами в `.github/workflows/`, там же настроен CI.

**Оформление коммитов.** На фронтенде подключены `husky` и `commitlint`, поэтому сообщения коммитов соответствуют Conventional Commits — по истории видно тип изменения и затронутую область.

Локально историю можно посмотреть так:

```bash
git log --oneline --graph --decorate --all   # вся история со всеми ветками
git shortlog -sne                            # вклад по авторам
```
